## Manual reserve-first DOI publication

This is an alternative for a specifically owner-authorized object, not a
universal prerequisite for the authorized existing public automatic integration.

1. Create the authorized Zenodo draft without publishing and reserve its DOI.
2. Independently verify its reservation, object, version, and access metadata.
   A reserved DOI is not a published deposit. Record it as reserved, not as
   an already published source identity; preserve historical references.
3. Prepare and re-render that object's DOI-bearing manuscript, inspect outputs,
   and retain actual checksums.
4. Upload/publish only the authorized object, then independently verify its
   repository, tag, version, and deposited contents. A local assertion or
   metadata test does not prove a deposit exists.

Never guess a DOI or give an earlier object's DOI to later source. Inspect
authenticated hooks immediately before a GitHub Release. The November 8, 2026
owner authorization covered that campaign's existing public integrations, not
blanket future publication. For a future owner-authorized release, retain the
authorized existing hook and verify the resulting archive's actual identity
and contents. Without explicit archive-publication authority, a Zenodo hook
or inconclusive observation still blocks the Release object.
PyPI publication, private-source disclosure, and new deposit automation for
private Violet, Copper, and Iron remain unauthorized.

After release, changes to `main` require another version. Do not amend the
published tag to add a DOI; plan metadata and re-rendering as a new versioned
change while preserving the prior archive reference.
