# Worked envelopes — provenance

Four real `line.report-envelope/1.0` records, one per line, each generated by
running that line's OWN public API inside that line's own repository and
virtual environment on 2026-07-29, and stored here **by value** under the
published schema. Nothing here was produced by importing a line package from
this repository; `tests/test_no_mocks.py` and `tests/test_standalone.py`
continue to hold that boundary, and these files are data the lines exported
for exactly this kind of transport.

This is the first cross-work data flow in the set, so the boundary is stated
precisely: each file is the verbatim output of the exporting line's
`canonical_envelope` over a worked case that line itself ships. The register
stores the records and never parses, compares, ranks, averages, or merges
their `native_status` values — for two of these files that value is a
complete per-record state list, for the other two a single word in that
instrument's vocabulary, and the difference is the point.

| File | Exporting repo (version) | Command run there | native_status shape |
| --- | --- | --- | --- |
| `white_line_worked.json` | white_line 0.7.0 | `worked_report()` → `report_envelope(...)` → `canonical_envelope(...)` | ordered per-record state pairs |
| `black_line_worked.json` | black_line 0.3.0 | `evaluate_work(SURFACES_ATTEMPT, as_of=SURFACES_AS_OF, max_evidence_age_days=SURFACES_WINDOW)` → `assessment_envelope(...)` → `canonical_envelope(...)` | one status word |
| `golden_line_worked.json` | golden_line 0.4.0 | `progress_report([two admitted entries], as_of="2026-07-29")` → `report_envelope(...)` → `canonical_envelope(...)` | ordered per-aspiration pairs |
| `red_line_worked.json` | red_line 0.3.0 | `review_engagement(action("Targeting component…", {"targeting"}), reviewed_on="2026-07-15")` → `finding_envelope(...)` → `canonical_envelope(...)` | one classification word |

Each file's `report_ref` is the exporting line's SHA-256 pointer to its
complete canonical native report; the register stores the pointer and cannot
dereference it — the referenced report lives in the exporting repository's
API, not here.

**Subjects differ on purpose.** The four envelopes describe four different
worked cases, each named in its exporting line's own reference scheme. They
are co-registered in `tests/test_worked_example.py` to exercise the
register's real intake, relation, projection, and metric machinery over real
exported data — NOT to assert that four instruments witnessed one work. That
distinction is carried in the test's relation records (`CANNOT_COMPARE`) and
in an open return contract that forbids the favorable posture until a
same-subject co-registration actually exists.

Regeneration: re-run the commands above in each line's repository and
overwrite these files. A regenerated file may differ if the exporting line's
worked case, registry, or version moved; the test suite reads whatever is on
disk and re-checks the shape, so a stale pointer fails loudly rather than
silently.

acceptance condition: four envelopes about ONE declared work. These four
records meet it. The declared subject is **witness_register 0.1.0 itself**
(commits 56962fe + 49ebea4, 2026-07-29), and the registrar (the operator's
assistant, recorded as such in each `subject_id`) authored each instrument's
inputs from the repository's own records:

| File | Native verdict | What was declared/observed (all real artifacts) |
| --- | --- | --- |
| `black_line_same_subject.json` | `ALIGNED` | all 22 required labels declared, each `source_snapshot_ref` naming the artifact behind it (manuscript sections, CHANGELOG hardening entry, tests, uv.lock, git commits, TODO, correspondence, provenance README) |

observations were filed by the assistant operating the instruments, not by

verdicts themselves are what each line's real evaluator returned.
